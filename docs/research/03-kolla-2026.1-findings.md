## Configuration as code

- The CLI's `--configdir DIR` loads `DIR/globals.yml`, then `DIR/globals.d/*.yml` in sorted order, then `DIR/passwords.yml`. `node_custom_config` is `DIR/config`. Vault flags pass through (`--vault-id`, `--vault-password-file`). **VERIFIED** — KA/kolla_ansible/ansible.py
- `kolla-readpwd` / `kolla-writepwd` store `passwords.yml` in Vault through `hvac`, using **KV v2 only**, a `--vault-mount-point` (default `kv`), AppRole or token auth, and `--vault-cacert`. **VERIFIED** — https://opendev.org/openstack/kolla-ansible/raw/branch/master/kolla_ansible/cmd/readpwd.py. akasha points these at OpenBao (KV v2, API-compatible; **INFERRED**, untested). See [07](07-trust-and-data.md).
- `validate-config` and `prechecks` need real hosts, so run them from the bastion. GitHub-hosted CI only lints. **INFERRED**

## Low-RAM tuning for this lab

Rationale: a tuned controller is about 4–6.5 GB (**ESTIMATED**); see [02](02-topology-and-nesting.md). Values marked ESTIMATED are judgement calls.

```yaml
# globals.d/40-tuning.yml
openstack_service_workers: 1
openstack_service_rpc_workers: 1
enable_fluentd: "no"
enable_heat: "no"
enable_cinder_backup: "no"
mariadb_innodb_log_file_size_mb: 256             # ESTIMATED
memcached_max_memory: "64"                        # ESTIMATED
rabbitmq_extra_config:
  vm_memory_high_watermark.absolute: "512MiB"     # ESTIMATED; RabbitMQ advises absolute limits in containers
```

```ini
# config/galera.cnf
[mysqld]
innodb_buffer_pool_size = 512M        # ESTIMATED
# config/nova/nova-compute.conf
[DEFAULT]
reserved_host_memory_mb = 1536        # raise to the measured overhead (≈1.8–2.6 GB)
ram_allocation_ratio = 1.0
resume_guests_state_on_host_boot = true
```

- RabbitMQ memory guidance: https://www.rabbitmq.com/docs/memory **VERIFIED**
- Per-container hard caps (`dimensions`/`mem_limit`) also exist: https://docs.openstack.org/kolla-ansible/latest/reference/deployment-config/resource-constraints.html **VERIFIED**

## TLS

- `kolla_enable_tls_internal` is off by default. `kolla_enable_tls_external` follows it only when both VIPs are the same, so set it explicitly. **VERIFIED** — KA/ansible/group_vars/all/haproxy.yml
- Certificates: `haproxy.pem` and `haproxy-internal.pem`, plus `kolla_copy_ca_into_containers`, `openstack_cacert` and `kolla_admin_openrc_cacert`. **VERIFIED** — https://docs.openstack.org/kolla-ansible/latest/admin/tls.html
- `kolla-ansible certificates` produces a test CA that is "not suitable for a production deployment". **VERIFIED**
- Database TLS requires ProxySQL. **VERIFIED** — common.yml
- Plan: issue the HAProxy certificates from the OpenBao intermediate CA, with internal and external TLS on and backend TLS deferred. **INFERRED**

## Backups and upgrades

- **Backups:** set `enable_mariabackup: yes`, then run `kolla-ansible mariadb-backup [--incremental]`. Output goes to the `mariadb_backup` Docker volume. Kolla does not schedule it (use cron), and restore is manual. **VERIFIED** — https://docs.openstack.org/kolla-ansible/2026.2/admin/mariadb-backup-and-restore.html
- **Upgrades:** `pip install` the new branch → `install-deps` → `kolla-mergepwd` → `pull` → `prechecks` → `upgrade`. SLURP jumps first need ansible-core and RabbitMQ intermediate steps. RabbitMQ allows one minor version per step unless the version is listed in `rabbitmq_allowed_upgrades`. **VERIFIED** — https://docs.openstack.org/kolla-ansible/latest/user/operating-kolla.html
- Before 2027.1, check the Khepri feature flag (`rabbitmqctl list_feature_flags | grep khepri`). **INFERRED**
- **Password rotation:** blank the entry, run `kolla-genpwd -p`, then `reconfigure`. **VERIFIED** — https://docs.openstack.org/kolla-ansible/latest/admin/password-rotation.html

## Power loss and reboot: UNRESOLVED, must be tested

- **What is verified:**
  - Containers use `docker_restart_policy: unless-stopped`. **VERIFIED** — common.yml
  - With one node, `wsrep_cluster_address=gcomm://` is empty. **VERIFIED** — galera.cnf.j2
  - Kolla's original design note says an AIO "can recover from power outage without additional configuration". **VERIFIED** — https://opendev.org/openstack/kolla/commit/2aaaed770e158c3dc0d6e1895021c0e0475d200d
  - Galera docs say that after a hard crash every node has `safe_to_bootstrap: 0`. **VERIFIED** — https://galeracluster.com/library/training/tutorials/restarting-cluster.html
- **Test plan:**
  1. `virsh destroy os-ctl01`, then start it again.
  2. Watch the `mariadb` container.
  3. If it loops on "may not be safe to bootstrap", run `kolla-ansible mariadb-recovery`, which compares seqno and bootstraps. **VERIFIED** — recover_cluster.yml
  4. Record the result in a runbook.
- **OVN and RabbitMQ:**
  - OVN NB/SB run as single-member raft clusters, which should re-elect themselves. **INFERRED**
  - RabbitMQ should restart cleanly; if it does not, run `kolla-ansible rabbitmq-reset-state`. **INFERRED**
- **Boot order:** libvirt has no autostart ordering. **VERIFIED** — https://lists.libvirt.org/archives/list/users@lists.libvirt.org/thread/FBPVJPIIGSG65MZ4B3LQSAT675BG7WWQ/
  - Plan: a systemd unit on the host that starts OPNsense → bastion → core → ctl01, waits for healthy `mariadb`/`rabbitmq`/`ovn_nb_db`, then starts cmp01/02.
  - Shutdown uses reverse order through `libvirt-guests`.
  - Install Kolla's `tools/kolla-libvirt-guests-docker.service` on the computes. **VERIFIED** — KA/tools

## Octavia with the OVN provider

- Settings: `enable_octavia: yes`, `octavia_provider_drivers: "ovn:OVN provider"`, `octavia_provider_agents: "ovn"`. Amphora-only settings switch off on their own. **VERIFIED** — https://docs.openstack.org/kolla-ansible/latest/reference/networking/octavia.html
- Limits: L4 only (TCP/UDP/SCTP), `SOURCE_IP_PORT` only, TCP/UDP-CONNECT health monitors only, no mixed IPv4/IPv6. **VERIFIED** — https://docs.openstack.org/ovn-octavia-provider/latest/admin/driver.html
- RAM: about 0.3–0.5 GB, with no amphora VMs. **ESTIMATED**
- Pattern: one L4 load balancer in front of an in-cluster L7 ingress. Red Hat documents the OVN provider for OpenShift on OpenStack. **VERIFIED** — https://docs.redhat.com/de/documentation/openshift_container_platform/4.13/html/networking/load-balancing-openstack
