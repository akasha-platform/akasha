## Configuration as code

- The CLI's `--configdir DIR` loads `DIR/globals.yml`, then `DIR/globals.d/*.yml` in sorted order, then `DIR/passwords.yml`. `node_custom_config` is `DIR/config`. Vault flags pass through (`--vault-id`, `--vault-password-file`). **VERIFIED** — KA/kolla_ansible/ansible.py
- `validate-config` and `prechecks` need real hosts, so run them from the bastion. GitHub-hosted CI only lints (yamllint, gitleaks, a check that no `passwords.yml` in clear is committed). **INFERRED**

### Installation on the deployment host (bastion)

```bash
python3 -m venv /opt/kolla
/opt/kolla/bin/pip install 'kolla-ansible==22.2.0'   # OPEN: or git+https://opendev.org/openstack/kolla-ansible@<stable/2026.1 SHA>
/opt/kolla/bin/kolla-ansible install-deps
/opt/kolla/bin/kolla-ansible <cmd> --configdir <repo>/infra/kolla -i <repo>/infra/kolla/multinode
```

Upstream recommends installing from the stable branch; pinning a release or a SHA is the reproducible choice. Which of the two to pin is an **open decision**. **VERIFIED** (recommendation) — KA/doc/source/user/operating-kolla.rst

### Passwords from OpenBao

- `kolla-readpwd` / `kolla-writepwd` store `passwords.yml` in Vault through `hvac`, using **KV v2 only**, a `--vault-mount-point` (default `kv`), AppRole or token auth, and `--vault-cacert`. **VERIFIED** — cited from the **master** branch: https://opendev.org/openstack/kolla-ansible/raw/branch/master/kolla_ansible/cmd/readpwd.py (verify the same code in stable/2026.1). OpenBao exposes a Vault-compatible KV v2 API, so this should work. **INFERRED, untested**
- `kolla-genpwd` and `kolla-mergepwd` need the plaintext file. Flow: generate/merge on a tmpfs (`/dev/shm`), `kolla-writepwd` into OpenBao, delete the file; at deploy time `kolla-readpwd` → tmpfs → run Kolla → delete. `passwords.yml` must exist while Kolla runs. **INFERRED**

## Low-RAM tuning and the controller budget

- A tuned controller is about **4–6.5 GB** (**ESTIMATED**, workers=1, no Heat/fluentd); Octavia adds ~0.3–0.5 GB and Kolla's Prometheus server ~0.3–0.5 GB (**ESTIMATED**).
- **OOM risk on an 8 GB ctl01** (details and sources in [02](02-topology-and-nesting.md)): a 2026.1 AIO measured ~12.3 GB after deploy; a lab OVN controller "about 10GB"; Kolla CI hit the OOM killer on 8 GB nodes during Octavia tests. Mitigation: measure (`docker stats --no-stream`, `smem`), tune, defer Octavia if needed.

## Identity, tenancy, images

- **Model** (**INFERRED** design; facts **VERIFIED** where tagged):
  - Domain `akasha`; projects `platform` (K3s VMs) and optionally `sandbox`.
  - Users `svc-terraform` (member on `platform`) and `svc-k8s-ccm` (`member` + `load-balancer_member`, the pair Octavia needs under Secure RBAC); `reader` for monitoring.
  - Two OpenTofu stacks: an **admin** stack (domain, projects, users, role assignments, quotas, flavors, public images, external network) and an **application-credential** stack as `svc-terraform` (networks, routers, security groups, ports, instances, volumes).
- **Application credentials:** `unrestricted=false` by default; changing `roles` or `access_rules` forces replacement; they always belong to the user who creates them, so create them through a provider alias logged in as the service user, or once by CLI and store them in OpenBao. **VERIFIED** — https://docs.selectel.ru/en/terraform/openstack-provider-reference/identity-keystone/resources/openstack_identity_application_credential_v3.md
- For the cloud-controller-manager, prefer **role-limited** credentials over `access_rules`: the CCM calls many Nova, Neutron and Octavia paths, so access rules break easily. **INFERRED**
- **Images:** Debian 13 genericcloud qcow2 (dated directory + SHA512SUMS) with properties `os_distro=debian`, `hw_qemu_guest_agent=yes`, `hw_disk_bus=scsi`, `hw_scsi_model=virtio-scsi`; install `qemu-guest-agent` via cloud-init. **VERIFIED** — https://docs.openstack.org/glance/latest/admin/useful-image-properties.html
- **Glance storage:** the default file backend stores images on ctl01's `glance` volume, so size ctl01's disk for the image set. **VERIFIED** (`glance_backend_file` default)

- Certificates: `haproxy.pem` and `haproxy-internal.pem`, plus `kolla_copy_ca_into_containers`, `openstack_cacert` and `kolla_admin_openrc_cacert`. **VERIFIED** — https://docs.openstack.org/kolla-ansible/latest/admin/tls.html

## Monitoring and logs

- **Prometheus:** off by default. Option 1 (first step): `enable_prometheus: "yes"` with 7-day retention on ctl01 (~0.3–0.5 GB, **ESTIMATED**). Option 2: exporters only (`enable_prometheus_server: "no"`, `enable_prometheus_alertmanager: "no"`), scraped by the Kubernetes Prometheus, which needs a route from K3s to the management network. **VERIFIED** (flags) / **INFERRED** (end-to-end) — KA/ansible/group_vars/all/prometheus.yml
- Exporters available: node, cadvisor, mysqld, memcached, haproxy, rabbitmq plugin, openstack-exporter, blackbox, libvirt, openstack-network-exporter (2026.1). **VERIFIED** — same file
- **Host scraping:** `prometheus_node_exporter_targets_extra` adds hosts outside Kolla (the physical host), and custom jobs go in `{{ node_custom_config }}/prometheus/prometheus.yml.d`. **VERIFIED** — https://docs.openstack.org/kolla-ansible/2026.1/reference/logging-and-monitoring/prometheus-guide.html
- **Logs without fluentd:** services still write to the `kolla_logs` volume (`/var/log/kolla`); the cron container rotates daily, keeps 6, max 100 MB. Ship them with Grafana Alloy to Loki in Kubernetes, or keep them local. **VERIFIED** (rotation) — KA/ansible/roles/cron/defaults/main.yml; **INFERRED** (Alloy)

## Backups and upgrades

- **Backups:** set `enable_mariabackup: yes`, then run `kolla-ansible mariadb-backup [--incremental]`. Output goes to the `mariadb_backup` Docker volume. Kolla does not schedule it, and restore is manual. Upstream suggests a **daily full kept 2 weeks and an hourly incremental kept 1 day**. The command does not need `passwords.yml`, so a cron job on the bastion works; then restic the volume off-host. **VERIFIED** — https://docs.openstack.org/kolla-ansible/2026.2/admin/mariadb-backup-and-restore.html
- **Upgrades:** `pip install` the new branch → `install-deps` → diff inventory with the new sample → `kolla-mergepwd` → `pull` → `prechecks` → `upgrade` → `check`. SLURP jumps first need ansible-core and RabbitMQ intermediate steps. RabbitMQ allows one minor version per step unless listed in `rabbitmq_allowed_upgrades`. **VERIFIED** — https://docs.openstack.org/kolla-ansible/latest/user/operating-kolla.html
- **Upgrade rehearsal:** offline libvirt snapshots of all VMs and a fresh `mariadb-backup` before starting. **INFERRED**
- Before 2027.1, check the Khepri feature flag (`rabbitmqctl list_feature_flags | grep khepri`). **INFERRED**
- **Password rotation:** blank the entry, run `kolla-genpwd -p`, then `reconfigure`. **VERIFIED** — https://docs.openstack.org/kolla-ansible/latest/admin/password-rotation.html

## Power loss and reboot: UNRESOLVED, must be tested

- **What is verified:**
  - Containers use `docker_restart_policy: unless-stopped`. **VERIFIED** — common.yml
  - With one node, `wsrep_cluster_address=gcomm://` is empty. **VERIFIED** — galera.cnf.j2
  - Kolla's original design note says an AIO "can recover from power outage without additional configuration". **VERIFIED** — https://opendev.org/openstack/kolla/commit/2aaaed770e158c3dc0d6e1895021c0e0475d200d
  - Galera docs say that after a hard crash every node has `safe_to_bootstrap: 0`. **VERIFIED** — https://galeracluster.com/library/training/tutorials/restarting-cluster.html
  - An older bug left containers **without a restart policy after `mariadb-recovery`**; it is fixed, but check `docker inspect` after a recovery. **VERIFIED** — https://gitea09.opendev.org:3081/openstack/kolla-ansible/commit/f979ae1f8ee182a8bc6fde4b23b95a460cb81488
- **Test plan:**
  1. `virsh destroy os-ctl01`, then start it again.
  2. Watch the `mariadb` container.
  3. If it loops on "may not be safe to bootstrap", run `kolla-ansible mariadb-recovery`, which compares seqno and bootstraps. **VERIFIED** — recover_cluster.yml
  4. Record the result in a runbook.
- **OVN and RabbitMQ:**
  - OVN NB/SB run as single-member raft clusters, which should re-elect themselves. **INFERRED**
  - RabbitMQ should restart cleanly; if it does not, run `kolla-ansible rabbitmq-reset-state`. **INFERRED**
- **Boot order:** libvirt has no autostart ordering. **VERIFIED** — https://lists.libvirt.org/archives/list/users@lists.libvirt.org/thread/FBPVJPIIGSG65MZ4B3LQSAT675BG7WWQ/
  - Plan: disable autostart for every VM except OPNsense; a systemd unit on the host starts OPNsense → waits for the gateway → bastion → core → ctl01 → waits for healthy `mariadb`/`rabbitmq`/`ovn_nb_db` (`docker inspect --format '{{.State.Health.Status}}'` over SSH) → cmp01/02. **INFERRED**
  - Shutdown in reverse order through `libvirt-guests` with `ON_SHUTDOWN=shutdown` and `PARALLEL_SHUTDOWN=0`. **INFERRED**
  - Install Kolla's `tools/kolla-libvirt-guests-docker.service` on the computes so Nova guests shut down cleanly. **VERIFIED** — KA/tools
- **Post-boot health script:** `openstack compute service list`, `openstack network agent list`, `openstack volume service list`, check the `cinder-volumes` VG and iSCSI (tgtd), then `kolla-ansible check`. **INFERRED**

## Octavia with the OVN provider

- Settings: `enable_octavia: yes`, `octavia_provider_drivers: "ovn:OVN provider"`, `octavia_provider_agents: "ovn"`. Amphora-only settings (`octavia_auto_configure`, jobboard) switch off on their own. **VERIFIED** — https://docs.openstack.org/kolla-ansible/latest/reference/networking/octavia.html
- Limits: L4 only (TCP/UDP/SCTP), `SOURCE_IP_PORT` only, TCP/UDP-CONNECT health monitors only, no mixed IPv4/IPv6. **VERIFIED** — https://docs.openstack.org/ovn-octavia-provider/latest/admin/driver.html
- RAM: about 0.3–0.5 GB, with no amphora VMs. **ESTIMATED**
- Pattern: one L4 load balancer in front of an in-cluster L7 ingress. Red Hat documents the OVN provider for OpenShift on OpenStack. **VERIFIED** — https://docs.redhat.com/de/documentation/openshift_container_platform/4.13/html/networking/load-balancing-openstack
